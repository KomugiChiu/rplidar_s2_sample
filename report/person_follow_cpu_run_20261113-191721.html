7. cpu_nodes.csv 與 namespace 修正

這一筆 run 是 cpu_nodes.csv 首次上線；數值正確，但相機標籤當時還沒合併 namespace。

t_unix,pid,node,process,cpu_pct,rss_mb,threads,read_kb,write_kb,aggregate

修正前

__node:=camera → /camera （漏掉 __ns:=/camera）

修正後

__ns:=/camera + __node:=camera → /camera/camera

修正內容（monitor_cpu.py）

  • 解析 __ns:=<ns>
  • 合併 __ns + __node，避免 // 或重複前綴
  • 只有 __ns 沒有 __node 時，用已知對應表或 process name 補齊
  • __node 已是絕對名稱時不再前置 namespace

板端實測

__ns:=/camera + __node:=camera → /camera/camera __node:=test_node → /test_node __ns:=/foo + __node:=bar → /foo/bar

8. 結論

這一筆跟隨的 CPU 狀況健康： 跟隨期間 mean 50.5%、p95 65.2%、max 67.5%，每顆核心都低於 70%。
  • 整段 p95 91.9% / max 94.3% 來自 +0~10 s 啟動與 bag discovery，以及 +71.7 s 停止時 /slam_toolbox finalize（單核 max 100.5%，四核 25.1%），不是跟隨負載。
  • 最大固定成本是 AI 與相機：跟隨期間合計 23.9%（12.2 + 11.7）。
  • SLAM 跟隨期間只有 3.4%，最高 14.1%，不是這一筆的瓶頸。
  • Nav2 + demo + recovery 合計 8.8%，其中 controller 2.1%、driver 2.0%、collision 1.8%。
  • lite bag + monitor 約 9.3%（四核），bag lost 只有 2 筆，目前預設值可繼續使用。
  • cpu_nodes.csv 的 namespace 已修正，之後的 run 會直接標成 /camera/camera。

9. 建議

  • 若要再降 CPU，優先動相機：640×480 @ 15 → 424×240 @ 15，RealSense 約可從四核 11.5~12% 降到 5~6%。
  • 沒用到的 Nav2 node 可關：docking_server、route_server、smoother_server、waypoint_follower、keepout_container。
  • /slam_toolbox 的四核 25.1%（單核 100.5%）只出現在停止瞬間，不影響跟隨；若之後出現跟隨中四核 >20%（單核 >80%）再處理。
  • 視覺置中這次 started 8 次、timeout 2 次，可考慮把 visual_rotation_timeout_sec 調到 4~5 秒。
