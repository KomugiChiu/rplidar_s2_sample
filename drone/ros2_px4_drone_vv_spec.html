01

目的、範圍與用語

本節界定驗證與確認的分工、本規格書涵蓋的系統邊界，以及後續章節共用的判讀基礎。兩個用語在後續章節中固定使用本節定義，不再另行解釋。

Verification（驗證）

定義：判斷系統是否符合規格文件所載需求，即確認團隊「做對的事」。於本專案中對應各階段測試，包含 V1 SITL 的需求項測試、V3 台架驗收、V4 繫留飛行與 V5 室內自由實飛；輸出為測試案例的通過或失敗紀錄，並回填第 4 節矩陣。

Validation（確認）

定義：判斷系統是否滿足原始任務意圖，即確認團隊「做出對的系統」。任務意圖由避障、路徑規劃、測距融合、VIO 與 AprilTag 降落所構成的自主任務所定義，於本專案中對應 M5 完整任務展示與利害關係人驗收。

範圍

下表界定本規格書的適用邊界。範圍外項目不由本規格書的測試案例涵蓋，亦不作為 M5 確認的判定依據。

範圍內 範圍外
PX4 飛控行為、ROS 2 自主堆疊、通訊橋接、動力性能、failsafe、實飛程序 供應商內部製程、馬達與電池的破壞性測試、法規適航認證

邊界原則

飛控行為以 PX4 出廠參數集與介面凍結版本為基準驗證；供應商製程能力以出廠測試報告與台架數據為證據，不由本團隊重複執行破壞性試驗。法規適航認證屬範圍外事項，其缺項不阻擋 M5 的技術確認，但須於確認紀錄中註明。

02

V&V 策略與階層

驗證活動依風險遞增分為六層，每層的失敗成本遠低於下一層；全部需求在越低層完成驗證越佳。同一需求若能在 V1 收斂，即不在 V5 重複取證，僅保留實機環境特有的項目於高層執行。

驗證階層與成本梯度

V0 → V6 
V0  紙上分析與介面檢核        （設計文件、推力計算、參數審查）
V1  SITL 軟體迴路             （PX4 SITL + Gazebo，CI 可自動化）
V2  HITL 硬體迴路             （真實飛控接回模擬世界）
V3  台架驗收                   （vendor spec 第 5 節 checklist A–G）
V4  繫留飛行                   （安全繩束縛下驗證融合與動力）
V5  室內自由實飛               （定點、航點、低速避障、降落）
V6  完整任務確認               （起飛 → 避障穿越 → AprilTag 降落 = M5）
風險與成本遞增 ↓；發現問題的期望成本遞減 ↑

← 可水平捲動 →

階層與里程碑的對照如下。V0 與 V2 不獨立對應里程碑，分別作為設計審查與硬體迴路的過渡層；V3 於 dev kit 到位後執行，V5 安排於 W15–18。

層級 對應里程碑 主要驗證內容
V1 M1 offboard 控制、VIO 餵入 EKF2、GPS-denied 懸停
V1 M2、M3 避障穿越、AprilTag 模擬降落
V3 —（dev kit 台架） 測距儀融合、failsafe 演練、動力序
V4 M4 繫留定點、EKF 無發散、振動
V5 —（W15–18） 自由飛行定點、低速避障、實機降落
V6 M5 完整任務流程

階層選擇原則

涉及安全邏輯的需求（SAF、COM 組）不得僅於模擬層結案，至少須於 V1 驗證行為、於 V4 或 V5 驗證實機環境下的時間特性。涉及環境物理的需求（振動、氣流、感測器曝光）不得以 SITL 結果替代實飛證據。

03

驗證方法、測試案例與問題分類

每條需求指定一種主要驗證方法，方法代碼沿用 INCOSE 慣例並於本節固定定義。方法欄出現兩個代碼時，以斜線分隔的方法互為佐證，兩者皆須完成。

代碼 方法 說明
T Test 執行量測並記錄數據（頻率、誤差、溫度）
A Analysis 以計算或既有數據佐證（推力表、續航算式）
I Inspection 目視或文件核對（參數集 diff、線序圖）
D Demonstration 操作演示不量測（QGC 連線、模式切換）

測試案例命名

測試案例以 TC-<需求ID>-<兩位序號> 命名，例如 TC-SAF-001-01 為 SAF-001 的第一個測試案例。同一需求於不同層級執行時，序號連續編派並於紀錄中標明層級，避免不同環境的結果互相覆蓋。

問題嚴重度

測試失敗或現場異常一律開立問題單並分級。分級決定處理時限與回歸範圍，不得由執行者自行降級；降級須經 task leader 書面同意。

等級 定義 處理時限
S1 危及安全或阻斷任務（飛行中失聯、EKF 發散、失控） 立即中止活動，修復並全量回歸後重驗
S2 功能失效但不危及安全（避障未觸發、降落誤差超標） 3 個工作日內修復
S3 性能偏差（頻率略低、延遲偏高但未超標） 下一整合日前修復
S4 文件或顯示問題 下一版次修正

回歸規則

  1. S1 修復後：執行全量回歸，範圍為 V1 CI 全項加上受影響層級的全部測試案例；重驗通過前該層級不得恢復活動。
  2. S2 修復後：執行受影響需求項與其上游依賴項；依賴關係以第 4 節矩陣與第 9 節追溯表判定。
  3. 整合日：每次整合日（週三）執行 V1 CI 全量回歸，結果作為當週 S3 問題的結案依據。
04

矩陣逐條列出需求、來源、驗證方法、執行層級與通過準則；需求編號沿用本規格書定義，來源欄指向既有文件章節。矩陣為測試案例編派、回歸範圍判定與簽核的共同依據，任何需求新增或準則修訂皆須同步更新本節。

矩陣分七組呈現。同一需求於不同層級可有不同準則時，以多列呈現並於該組末尾說明；層級欄的範圍表示該需求須於範圍內每一層級取得證據。

05

各層級進入與退出準則

層級推進採進入與退出雙閘門：進入準則確保環境與設備就緒，退出準則確保該層應取得的需求證據完整。任一準則未滿足即不得進入下一層，亦不得以「後續層級補驗」作為例外。

層級 進入準則 退出準則
V1 環境建置完成；課題世界與自訂車型就緒 SYS-001~005、NAV-001~006、PER-001~002、SAF-003~004、COM-001~003 全數通過
V2 V1 退出 + dev kit 到位 同一份 ROS 堆疊不改碼於 HITL 運行通過
V3 供應商整機到位 + 台架就緒 vendor spec 第 5 節 A–G 全項 + PWR-001~008 通過
V4 V3 退出 + 繫留設備與安全官指派 NAV-002~003、PWR-007、SAF-005~006 於繫留下通過
V5 V4 退出 + 飛行區核准 定點、航點、低速避障、降落實測通過

V2 的定位

V2 的目的在驗證真實飛控與同一份 ROS 堆疊的介面行為，不以取得新需求證據為目標。HITL 通過後，V1 既有結果仍然有效；若 HITL 暴露韌體或時序差異，受影響需求回到 V1 重驗後再推進。

06

實飛測試程序

本節適用於 V4 以上的每一次飛行。程序分飛行前準備與中止條件兩部分，兩者於每次飛行前朗讀確認，並由安全官在場監督。

飛行前程序

  1. 任務簡報

    由 task leader 主持，說明當日測試案例、飛行區域、人員站位、中止條件與通訊方式；簡報完成後方可進行設備通電。

  2. 飛行區與人群管制

    確認飛行區淨空、護欄與警示標示就位、非必要人員退出作業半徑；繫留階段另須確認繩索固定點與張力。

  3. checklist 朗讀執行

    逐項朗讀並由第二人複核：起飛前 PX4 預檢、EKF 狀態、電池電壓、RC 接管測試。任一項未通過即停止當次飛行。

  4. 紀錄設備開機

    啟動 rosbag、PX4 ulog 與影像紀錄，確認寫入正常且時間同步；紀錄未啟動不得起飛。

中止條件

下列任一條件成立時立即中止並執行對應動作，動作完成後由安全官宣告現場狀態，其他人員不得自行恢復飛行。

  1. RC 接管失敗

    執行斷電保護動作；同批設備在原因釐清前停止使用。

  2. EKF 創新量發散或狀態非綠

    切手動並降落，降落後保存 ulog 供分析。

  3. VIO 中斷超過設定 timeout

    依 SAF-003 的參數行為處置，並記錄中斷時刻與感測器狀態。

  4. 電池低於 failsafe 值

    立即降落，不再執行剩餘測試案例。

  5. 任何 S1 現象

    中止當日全部飛行，開立問題單並進入第 8 節流程。

記錄要求

紀錄 內容 處理方式
rosbag 感測器、VIO、規劃與 offboard setpoint 全話題 以當次飛行編號命名並歸檔
PX4 ulog 飛控日誌 上傳 Flight Review 並保留連結
飛行紀錄表 測試案例、結果、中止事件與處置 由 TL 簽核

三項紀錄保存於 git repo 的 flights/ 目錄；大型 bag 以外部儲存連結與校驗碼登錄，目錄中保留索引與簽核紀錄。

07

確認（Validation）計畫

確認以 M5 完整任務展示執行，由 task leader 與利害關係人在場驗收。展示於課題場進行，使用與 V5 相同的軟體版本與參數集，不為展示另開分支或臨時調參。

步驟 內容 判定
1 起飛至任務高度 穩定、無人為介入
2 依規劃路徑穿越課題場障礙 無碰撞、無接管
3 於 AprilTag 區域上方接近 偵測連續、TF 穩定
4 方案 B 閉環降落 誤差 < 50 cm

判定準則

連續兩次全劇本無人為介入完成即確認通過；任何一次觸發中止條件則回饋至第 3 節問題流程。兩次展示之間允許更換電池與執行飛行前程序，不允許修改軟體、參數集或任務檔案。

確認紀錄

確認通過後，由 task leader 彙整兩次展示的 rosbag、ulog、飛行紀錄表與簽認頁，標註軟體版本與參數集雜湊值，歸檔於 flights/。紀錄中的版本資訊為後續任何修訂的比較基準。

不符合處理規則

  1. 供應商交付相關：與供應商交付相關的不符合（PWR、A–G 項）依供應商規格第 6 節變更管理處理，重驗以同一份台架清單執行。
  2. 介面凍結項：修復不得改動介面凍結項，確需變更時以文件版本更新並同步本規格書矩陣，並重新執行受影響層級的測試案例。

紀錄完整性

問題單須附可重現的證據：測試案例編號、層級、rosbag 或 ulog 檔名、發生時刻與處置動作。缺乏證據的問題單不進入修復排程，僅登記為觀察項。
